Calculations

CALC.tox

Layer: spatial logic
In: 2 POPs (point or shape)
Out: 1 CHOP

CALC measures how two spatial entities relate to each other: two points, a point and a shape, or two shapes. It reduces that relation to one control signal. Four measurements are available: centre-to-centre distance, signed distance to a surface, an inside/outside test, and a smooth fade between two concentric spheres. Together these are enough for most body-to-object interactions in the lab, such as proximity, entering a zone, and gradual transitions. They come from a single component with one predictable output.

Role in the setup

CALC turns geometry into control data. A typical setup has a tracked joint from Azure Kinect sensors on input 1 and a Virtual objects on input 2. The resulting CHOP drives any parameter: the opacity of a projected layer, the gain of a sound, the state of a scene.

Technical specification

Let A be input 1 and B be input 2.

  • Distance between points. The Euclidean distance between the centres of A and B:
    center_dist = ‖c_A − c_B‖ (metres).
  • Distance between shapes. The distance from A to the surface of B, or between the surfaces of A and B. The result is signed: positive outside, negative inside. This works for every closed shape. For boxes and cylinders, the distance is measured outward from the shape's centre, so values near edges and corners are slightly larger than the true Euclidean surface distance.
  • In or outside of a shape. A binary containment test: inside = 1 if A is inside B, otherwise 0.
  • Fade to sphere. A continuous value between the inner sphere (radius r_in) and the outer shell (radius r_out) of a sphere-type virtual object. It is 1 inside r_in, 0 beyond r_out, and changes smoothly in between. This makes a soft, non-binary interaction zone. It requires B to be a sphere with Outer shell turned on.

Virtual objects

virtual_object.tox

Layer: spatial logic
In: position (CHOP, optional)
Out: shape (POP, blue), position + size (CHOP, green)

A virtual object is an invisible geometric volume (a sphere, box or cylinder) that you place in the physical room for other components to interact with. It does not draw anything itself. It is a spatial definition that other components can measure against, listen to or display. It is the basic building block of the lab's interaction logic: zones, triggers, attractors and sound sources are all made from virtual objects.

Role in the setup

Virtual objects connect the tracked body to the content. A tracked hand has no meaning until it can be related to something. The virtual object provides that "something" in the shared room frame. Its shape output feeds Calculations and the Virtual object viewer. Its position output can place a sound source in Ambisonics sound control.

Technical specification

  • Primitives. You can choose a sphere (radius), a box (width X, height Y, depth Z) or a cylinder. Only the size fields that belong to the current shape are active.
  • Transform. Position XYZ and Rotate XYZ place the object in the room frame (metres; X = width, Y = height, Z = depth). If you wire a CHOP into the optional input, it drives the position, so an object can follow a tracked joint or an animated path.
  • Soft boundary. For spheres, Outer shell adds a second, larger radius around the core. The space between the two radii is a transition zone that CALC uses for its Fade to sphere calculation.
  • GPU geometry. Since the October 2026 revision, the shape is a POP (point operator), so geometry is processed on the GPU. Scenes with many objects stay responsive. Each object gets its own colour, which the viewer picks up automatically.
  • Closed volumes. Distances and inside/outside tests only make sense for closed shapes. All built-in primitives are closed.

Comments on Spatial Logic

Earlier versions, previous attempts and related tech.

  • Distance meter: a workshop on triggers based on position tracking, the forerunner of CALC.
  • Four calculators → CALC (October 2026): DIST_between_points, DIST_to_object, IN_or_OUT_object and FADE_to_sphere were merged into one component with one output. Distance now works for any closed shape.
  • SOP → POP (October 2026): virtual objects and the viewer moved from CPU geometry (SOPs) to GPU point operators (POPs), so scenes with many objects run faster.
  • Related: importing 3D meshes or point clouds (a workshop topic) as another way to define shapes in the room. Phone scanning apps (Polycam, Scaniverse) can capture real objects or the room itself for this.

Comments on Sensing

Earlier versions, previous attempts and related tech.

  • Before the component: Azure Kinect data was introduced in a workshop (Sensor data: how to connect and interact with an Azure Kinect sensor kit). Each project set up the sensor by hand from a quick guide.
  • Community tools: projects for calibrating and merging several Kinects in TouchDesigner (multiplekinectcalibration_touchdesigner, TDAzureMerger) were explored before the in-house fusion.
  • Switch phases: the first multi-sensor host used one sensor's data at a time and switched between sensors based on margins. This broke with more than one person, or when someone walked from one sensor's field of view into another's.
  • Group-first fusion: the next version grouped the sensors' bodies into people first and matched them with the previous frame afterwards. Numbers jumped (p1 → p2 → p3) whenever a sensor picked someone up or lost them.
  • Track-first fusion (current, since early October 2026): detections are matched with known people first, and new people are confirmed over 5 frames before they get a number. Several people are tracked at once with stable numbers. See Kinect host.
  • Frozen hands: an earlier fusion kept the last known position of joints that every sensor rated 0. Hands froze in place, in one test 2.5 m behind the body. Such joints are now averaged across all sensors.
  • Left/right swap correction: a fix based on the shoulder axis and the confidence of the face joints was tried in September 2026 and reverted, because it didn't improve real results.
  • Lag CHOP → One Euro filter: smoothing moved to the client and from a Lag CHOP to a One Euro filter. In a simulation of a fast hand swing, the lag trailed by 133 ms and the One Euro filter by 50 ms.
  • Camera as a proximity sensor (2023): an early snippet that used a plain camera image to detect nearness, before depth sensing was used.
  • Hardware lifecycle: the Azure Kinect DK went out of production in 2023. The working recommendation for a successor is the Orbbec Femto Bolt (see the Kinect host note).
  • Add: what was tried, what didn't work, and why.

Tools

Info

The Spatial Computing Lab (LUCAscl*) gives artists, students and researchers a shared set of custom TouchDesigner components ("toxes"). These components hide the lab's specific hardware behind a small number of stable interfaces. There are eight components, grouped into three layers:

  • Sensing: body tracking and camera images from Azure Kinect sensors.
  • Spatial logic: virtual objects, and calculations between bodies and objects.
  • Output: wall projection, floor projection and third-order ambisonic sound.

Together they let a user go from a tracked body in the room to an image or sound that responds to it, without rebuilding the lab's signal chain. The components are meant to be used both at home and in the lab. Projects can be prepared and simulated remotely, and then run at full resolution and with live sensor data on site. On the sound side, the components are complemented by a rendering patch in Max/MSP. This note describes the system the components belong to, the conventions they share and how the other notes in this collection fit together.

Azure Kinects calibration & decisionmaking

HOST.onstartup.toe

Host: Intel NUC, TouchDesigner
Layer: sensing (back end)
In: 3 × Azure Kinect
Out: fused skeletons (OSC), camera images (NDI)

The Kinect host is the computer that the three Azure Kinect sensors are connected to. It runs a TouchDesigner project that reads each sensor, calibrates its data into the room's coordinate frame, decides which bodies seen by which sensors belong to the same person, fuses those views into one skeleton per person, and publishes the result to the lab network. Users never open it. The Azure Kinect sensors and Azure Kinect cameras components on the workstation are its clients. Keeping sensing on its own machine means the processing for depth, body tracking and video encoding does not compete with rendering on the main workstation. It also means every project in the lab receives the same calibrated data.

Role in the setup

The host turns three independent sensors into one room-wide tracking system. It does three things:

  • Calibration: each sensor's data is moved from the sensor's own viewpoint into the shared room frame (metres; X = width, Y = height, Z = depth; Z = 0 at the centre wall).
  • Decision making and fusion: every frame, it decides which detections are the same person, which person they are, and which sensor to trust for each joint. Each person appears once, with a stable number (p1 … p8).
  • Distribution: every joint of every person goes out over OSC, together with presence flags and a heartbeat. Camera images go out as NDI video streams.

The host deliberately makes no choice on behalf of the user. It always sends everything. Which person and which joints a project uses is decided on the client side (see Azure Kinect sensors), so several projects or users can us

Azure Kinect sensors

Azure_Kinect_sensor.tox

Layer: sensing
In: none
Out: one CHOP per selected joint (tx ty tz, metres)

This component gives live three-dimensional positions of human body joints, measured by the lab's Azure Kinect sensors. You choose which joints you need, and each one gets its own outlet as a CHOP with the position in room coordinates. Several people can be tracked at the same time (active since the first week of October 2026): each copy of the component follows one person. When you are away from the lab, a mouse mode stands in for the tracked body. This lets you develop and test interaction logic without sensors, and the patch keeps the same structure in the lab.

Role in the setup

The component is the main way bodies enter the system. Its outputs feed:

  • Calculations, to relate a body to a virtual object
  • Virtual object viewer, to check the tracking
  • Ambisonics sound control, to place sound sources on a moving body

It is the client of the Kinect host. The host decides who is in the room and sends every joint of every person. This component decides what this project uses: which person, which joints, and what to output when there is no usable data. It covers position only. For images from the same sensors, use Azure Kinect cameras.

Azure_Kinect_camera.tox

Layer: sensing
In: none
Out: one TOP per sensor

This component gives the live image streams of the lab's three Azure Kinect sensors as TouchDesigner TOPs, one per sensor. It is for work that uses the camera image itself, such as live video in a projection, image analysis, or material for compositing. Virtual object viewer

virtual_object_viewer.tox

Layer: spatial logic (verification)
In: positions (CHOP), shapes (POP)
Out: 3D preview

The viewer shows tracked points and virtual objects together in one 3D scene of the lab. Its only job is to check that everything is where you expect it to be. It does not change any data. The physical room is otherwise blind to what the system "thinks", and the viewer makes that state visible. Most spatial interaction design depends on this view for debugging and for explaining a setup.

Role in the setup

Interaction logic in the lab is invisible: virtual objects have no physical form, and tracking errors cannot be seen in the room. The viewer is where the sensor layer and the spatial-logic layer can be checked together before content is connected to the outputs.

Technical specification

  • Scene. A wireframe box shows the physical room. Inside it, every tracked point wired into the green inputs is drawn as a sphere, and every Virtual objects in the project is drawn in its own colour.
  • Automatic discovery. Virtual objects in the project are found automatically. They do not need to be wired one by one.
  • Viewports. The perspective view gives a quick overall check. The top view works as a live floor plan, which is useful for placing zones relative to the entrance and the projection surfaces.
  • Read-only. The component has no side effects. You can add or remove it at any time without changing a patch's behaviour.

Floor projection

floor_projection.tox

Layer: output (image)
In: 1 TOP
Out: projection window + resolution CHOP (resX, resY)

This component is the output stage for the lab's floor projector. It works the same way as Wall projection, but for a roughly square surface with no natural "up". The floor matters in spatial computing because it is where tracked bodies, virtual objects and projected images line up most directly. A position in the room's XZ plane corresponds to a point on the floor image.

Role in the setup

The floor projection completes the lab's image output. It is especially suited to interaction based on location: zones, paths and traces that respond to where visitors stand. These are typically made by combining Azure Kinect sensors data with Virtual objects zones and Calculations.

Technical specification

  • Resolution contract. As with the wall projection, the component publishes resX, resY as a CHOP that you wire into your source TOP.
  • Recommended chain: moviefilein → fit → floor_projection. A Fit TOP before the component makes sure that content made for other aspect ratios (for example wide wall content) is fitted on purpose and not distorted.
  • Home/lab switch. License off = reduced home resolution (within the 1280 × 1280 limit of the Non-Commercial licence). On = full lab resolution (Educational licence on the lab workstation).
  • Orientation. The floor has no inherent up. By convention, orient the content towards where the audience enters (the south side, where the entrance is) and write the orientation down in the project documentation.
  • Mapping to room coordinates. Because the room frame uses X = width and Z = depth, positions from the sensor and from virtual objects can be mapped to floor pixel coordinates with a linear scale to resX, resY. This mapping is the user's responsibility, as the component does not apply it.

Wall projection

wall_projection.tox

Layer: output (image)
In: 1–3 TOPs
Out: projection window + resolution CHOP (resX, resY)

This component is the output stage for the lab's wall projectors. It opens the projection window, sends the images to the wall surfaces, and tells the user the exact resolution the source images must have, both at home and in the lab. The resolution comes from the component as a CHOP that the user wires into their own source. This keeps content and output in sync by design, so there is no stretching, cropping or black bars.

Role in the setup

Together with Floor projection and Ambisonics sound control, this component forms the lab's output layer. Any image from a project, whether generated, filmed (Azure Kinect cameras) or controlled by interaction logic, reaches the walls through this component.

Technical specification

  • Projection modes.

  • Panoramic projection: one wide image across the whole wall surface from input 1. Inputs 2 and 3 are ignored.
  • Single projection: output to one projector only, for tests and small setups.
  • Wall layout. The three channels correspond to the three fixed walls: left, centre and right as seen from the entrance (west, north and east). Ambisonics sound control

Ambisonics_sound_ctrl.tox

Layer: output (sound)
In: one position per source (CHOP) + audio (CHOP)
Out: third-order ambisonic mix on the lab's 16 + 1 loudspeaker array

This component places sound sources in the three-dimensional space of the lab. Each source has its own position, size and audio input, and the component renders them through the lab's third-order ambisonic loudspeaker system. The user works only in TouchDesigner: wire in a position (for example a Virtual objects or a tracked joint), point to an audio signal, and set a range. Encoding, decoding to the irregular speaker layout and transport over the Dante network are handled by a dedicated rendering chain in Max/MSP. This gives everyday users of the lab position-driven spatial sound, which would otherwise require specialist knowledge of ambisonics.

Role in the setup

This is the sound counterpart of Wall projection and Floor projection. It is where the spatial logic of a project becomes audible. A virtual object wired into a source makes that object heard at its location. A tracked joint makes a sound follow a body.

Technical specification

Signal chain

  1. TouchDesigner (HP Z8 workstation). The component holds one source per virtual object slot. Each source has a position (CHOP inlet), an audio input (a CHOP or channel) and a Rangegain. Audio is resampled automatically to the Dante network rate of 48 kHz. The internal network is built and wired by script, which re-checks the structure about once per second.
  2. Transport. Source positions are sent over OSC. Source audio is sent over Dante (Dante Via on the workstation, Dante Virtual Soundcard in ASIO mode on the rendering machine).

Max-MSP ambisonic renderer

Ambix_3th_order-sound_ctrl.maxpat

Host: Windows NUC, Max 9.1.5
Layer: output (sound, back end)
In: OSC positions (UDP 10000) + 16 audio channels over Dante
Out: 16 loudspeaker feeds + 1 subwoofer feed over Dante

This patch is the rendering engine behind Ambisonics sound control. It receives the positions of up to sixteen sound sources and their audio, encodes them into a third-order ambisonic sound field, and decodes that field to the lab's measured, irregular layout of sixteen loudspeakers plus a subwoofer, all in real time. Most users never touch it: the TouchDesigner component is the interface, and the renderer runs on a dedicated machine. Splitting the work this way keeps audio rendering apart from the graphics and tracking load on the main workstation. It also keeps the decoder calibration in one place, independent of any project.

Role in the setup

The renderer is the second half of the lab's spatial sound chain. Ambisonics sound control decides where each sound is and what it plays. The renderer turns that into speaker signals for this particular room. Because the calibration lives here, any TouchDesigner project that sends positions and audio in the expected format sounds correct in the lab without project-specific tuning.
