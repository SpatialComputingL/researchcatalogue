Lab tools: an introduction

Abstract

The Spatial Computing Lab (LUCAscl*) gives artists, students and researchers a shared set of custom TouchDesigner components ("toxes"). These components hide the lab's specific hardware behind a small number of stable interfaces. There are eight components, grouped into three layers:

  • Sensing: body tracking and camera images from Azure Kinect sensors.
  • Spatial logic: virtual objects, and calculations between bodies and objects.
  • Output: wall projection, floor projection and third-order ambisonic sound.

Together they let a user go from a tracked body in the room to an image or sound that responds to it, without rebuilding the lab's signal chain. The components are meant to be used both at home and in the lab. Projects can be prepared and simulated remotely, and then run at full resolution and with live sensor data on site. On the sound side, the components are complemented by a rendering patch in Max/MSP. This note describes the system the components belong to, the conventions they share and how the other notes in this collection fit together.

The lab as a technical system

The components are tied to one physical space and its hardware:

SubsystemConfiguration
Roomapprox. 5 × 5 × 3.5 m (width × depth × height). The entrance (the "gap") is on the south side.
Rigginga grid of scaffold pipes suspended below the concrete ceiling. It carries the sensors (on drop rods), the elevated loudspeakers and the projectors
Sensingthree Azure Kinect sensors (depth + RGB) mounted on the ceiling grid, used for skeleton tracking and as cameras
Imagethree fixed projection walls: left, centre and right as seen from the entrance (west, north and east). They can be used as three channels or one panoramic image. There is also a floor projection. A fourth (south) wall is mobile and is not installed by default.

Computingan HP Z8 workstation running TouchDesigner 2025.33230 with an Educational licence (content, tracking, control), and a Windows NUC running Max 9.1.5 (ambisonic rendering, see Max-MSP ambisonic renderer). The camera stream comes from a separate PC.
TransportDante audio network at 48 kHz (Dante Via on the workstation, Dante Virtual Soundcard on the NUC). OSC carries positions.

Shared conventions

All components follow the same conventions. Once you know them for one component, you know them for the rest.

  • Units and axes. Positions are in metres. X = width, Y = height, Z = depth. The sound system uses the same frame: Z = 0 is the north wall, Z increases towards the entrance, and the reference listening point is at X = 0, Y = 1.5 m (ear height), Z = 2.5 m (room centre).
  • Data types. Each component uses the native TouchDesigner family that fits the data:
  • images are TOPs
  • positions, distances and control values are CHOPs
  • geometry is POPs, the GPU-based point operators that replaced SOPs in October 2026
  • Configure pattern. Components that build their own outlets or windows (sensor, camera, projections) rebuild only when you press Configure. This keeps a running performance from being rebuilt by accident.
  • Named nulls. Users attach a named null to each outlet (null_head, null_cam_left, …) and work from those. If a component is reconfigured or updated, references to the nulls still work.
  • Home/lab parity. Every component that depends on the lab can run without it:
  • the skeleton sensor can follow the mouse instead of a body
  • the projection components have a License switch that changes between home resolution, which stays within the 1280 × 1280 limit of TouchDesigner's free Non-Commercial licence, and full lab resolution, which the lab's Educational licence allows.
  • all components behave the same either way, so a patch built at home runs unchanged in the lab.
  • "Normal, not bugs". Each component documents behaviour that looks like a fault but is expected, such as empty outputs outside the lab or a source that takes a moment to appear. This saves time when troubleshooting on site.

A typical interaction chain:

  1. A tracked joint (for example the right hand) comes from the sensor.
  2. A virtual object (for example a sphere with a soft outer shell) is placed in the room.
  3. CALC turns their spatial relation into one control value.
  4. That value drives the content, which reaches the audience through the wall and floor projections and through ambisonics sound control. The sound component can also take the virtual object's position directly, so the object can be heard in the room.

Each note has the same structure: abstract, role in the lab, technical description, parameters, outputs, limitations and relations to the other components. The shorter user READMEs are stored next to each .tox and inside the example .toe.

Project structure and updates

The components are distributed as one folder: an example .toe project file and a toxes folder that holds each .tox and its README.

  • Keep the .toe and the toxes folder together in one project folder with a name of your choice. This makes it easy to move the project between your own computer and the lab workstation.
  • You can rename the .toe freely. Do not rename the .tox files or their READMEs, because updates replace them by name.
  • To update a component, download the new .tox and replace the old one in the toxes folder. Components are built so that the parameter values stored in your project survive the update.
  • TouchDesigner does not autosave. Save often with Cmd/Ctrl + S. TouchDesigner keeps the numbered backups itself.

Revision, 2 October 2026 (SOP → POP).

  • virtual_object and virtual_object_viewer now output POPs, which run on the GPU, so scenes with many objects are noticeably faster.
  • Each virtual object has its own colour.
  • Four separate calculation components (DIST_between_points, DIST_to_object, IN_or_OUT_object, FADE_to_sphere) were replaced by one component, CALC. Its output channels are center_dist, shell_dist, inside and fade.
  • Patches made before this revision need to:
  • swap the old calculators for CALC
  • update their channel references
  • give a POP to anything that expected a SOP

Design rationale

The components follow one lesson from running the lab: visiting researchers have limited time on site, and that time should go to the parts of the work that need the physical room. Interfaces stay stable and the lab can be simulated, so most of the setup can be done remotely. Users can work with the lab at different depths:

  • treat each component as a black box
  • open it up and adapt it
  • skip it entirely and work with the raw data streams
